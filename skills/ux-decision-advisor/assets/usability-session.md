## Moderator script

Confirm consent and explain that the product is being tested, not the participant. Ask the participant to work as they normally would. State the think-aloud, assistance, and break rules. Do not reveal interface labels or the expected path.

Record observed behavior before interpretation. Distinguish slip, mistake, missing knowledge, environment interruption, and prototype limitation only when evidence supports the classification.

## Post-task questions

- “What did you think would happen after that action?”
- “What was clear or unclear at that point?”
- “How did you know you were finished?”
- “What would you do if this went wrong?”
- “Was this similar to anything you use normally?”

Use exact rating wording and balanced anchors. Do not ask “Did you like the new design better?” as a substitute for task evidence.

## Comparative design note

If two designs are compared, record condition order, practice tasks, task equivalence, carryover, fatigue, and version. Counterbalancing does not guarantee elimination of learning effects. A tiny formative sample can identify friction, not prove a population-level effect.

## Analysis and decision link

- Report attempted tasks, success/partial/failure, assistance, missing outcomes, and denominators.
- Report durations only with start/stop and failure/missing-time rules.
- Code issue severity using observable task/user consequence, not an opaque score.
- Link each issue to a design decision and disconfirming evidence.
- State prototype/environment and sample limitations.
