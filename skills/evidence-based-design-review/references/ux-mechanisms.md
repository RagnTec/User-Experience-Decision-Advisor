# User Task & Experience Explanation | v0.3

**体验评价必须以目标、任务与上下文为轴**。优先读取 `framework-selection.md` 选择相关原则，避免理论清单式点评。不要将用户视角简化为“站在用户角度想象心情”，也不要只把十条可用性启发式逐条套在截图上。

## 1. 从目标到体验因果链

一个完整的体验判断（若材料足够）应包含：

`用户的任务/目标 → 所看到或能操作的条件 → 需要进行的感知、理解、判断或动作 → 可能的成功/失败与恢复 → 体验后果 → 证据或不确定性`。

这是一条**假设生成和整理观察的分析链**，并不自行证明心理机制或因果关系。若没有真实行为证据，应使用“可能、在……条件下、需要验证”等措辞。

## 2. 只按相关性选择的分析视角

| 用户体验问题 | 可考虑的分析机制 | 需要的数据或证据 | 可能的反例 |
|---|---|---|---|
| 不知道现在发生了什么 | 系统状态可见、反馈与结果预期 | 界面状态、加载/失败/成功反馈 | 真实系统有声音/震动等其他通道 |
| 找不到下一步 | 信息组织、标签映射、可发现性、前序知识 | 任务流、交互稿、实际寻找行为 | 熟练用户有快捷路径 |
| 操作步骤复杂 | 工作记忆、切换成本、动作链、用户控制 | 步骤状态、操作记录、任务中断情况 | 额外确认可能在高后果任务中必要 |
| 误操作与难以恢复 | 错误预防、可撤销、反馈、恢复 | 错误路径、后果、恢复条件 | 系统已在其他渠道保存可恢复状态 |
| 信息过多难判断 | 注意分配、识别负担、主次层级 | 情境、并发信息、任务关键性 | 某些用户需要完整信息作决策 |
| 不同群体差异 | 能力、经验、接入条件、环境适配 | 有效用户分层与场景依据 | 不能把年龄/性别标签直接当能力变量 |
| 愉悦或偏好 | 满意度、控制感、信任与预期 | 访谈、量表、观察+谨慎解释 | 仅凭界面颜色不能认定用户喜好 |

每个选中的体验机制必须指向当前设计中的可见触点或用户观察，进一步写出可执行的修改/保留建议。不可仅以“违反启发式”作为结论。

以上是**可选机制清单**，不是“每个方案必须报告七维”。避免堆术语或用它们作为充分论据。

## 3. 实际行为与态度

- **观察事实**：用户完成/失败、重新尝试、停顿、求助、口述等；不要在没有工具测量时推测毫秒、眼动或心理生理指标。
- **态度/评价**：用户主观报告的易用、烦躁、偏好可如实呈现，但不能自动代表普遍用户或真实行为。
- **解释假设**：为什么某个行为出现，需要考虑系统状态、使用经验、任务理解、实验条件和替代原因。
- **输入资料的定性引语**：只有原始内容可核对时才引用；不得构造用户原声。

## 4. 不遗漏有效设计

即使任务是问题诊断，也要检查是否有**现有设计的正向贡献**，例如保留操作上下文、可恢复路径、减少必要步骤、改善状态清晰度等。若无法从材料确认优点，写“不足以判断”，不要机械夸奖。

## 5. E 报告的关键段落

1. 评价范围及证据类型（实际用户研究总结 or 设计材料体验预评估）。
2. 用户任务和关键情境，必要时标明产品定位由谁提供。
3. 沿真实材料所及的关键步骤分析**已有优势、潜在摩擦、认知/行为机制、重要边界**。
4. 体验影响只描述有依据的方向或已测结果；可用性包括有效性、效率和满意度，但不可把任务效率代理为主观满意度。
5. 给出设计启示及其适用条件，以及能够推翻解释的实证观察。

**不自动生成 Persona、完整旅程、情绪曲线、数值优先级或具象用户故事；除非来源确实支持。**
