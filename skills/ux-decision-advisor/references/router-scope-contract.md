# Shared Router Scope Contract | v0.4D.5

## Single core process; user-controlled analysis tracks

When a collaboration mode is known or provisionally inferred from the user task (see [Entry Mode Contract](entry-mode-contract.md)), every new Router-driven project uses the same **core decision context**: (1) define user request and real decision; (2) risk-proportionate jurisdiction/platform applicability precheck; (3) cognitive/physical human factors and binding-vs-convention applicability; (4) user/market/task context; (5) existing evidence and unknowns; (6) **user-confirmed analysis scope**; (7) deliver bounded professional result and next user-authorized step. These are professional context checks, not mandatory research tasks. Do not pre-create branches for VOC, surveys, interviews, Kano, market data collection or pilot monitoring.

**O** = explore user task, overlooked needs and candidate opportunities. **E** = evaluate a specified experience/design. **D** = compare alternatives and support a choice. **V** = design or analyze focused validation. Treat O/E/D/V as internal analysis capabilities, not a required end-user menu. A clear user request for explanation, analysis, decision comparison, or study-plan drafting permits **bounded advisory analysis** of that requested matter. If ambiguity would change the deliverable substantially, ask one targeted scope question rather than presenting all four categories.

Authorization remains strict: do not automatically initiate optional real-world research, ingest extra private files, make external API calls requiring authorization, expand to unrelated projects, perform regulated action, approve release, or treat proposed scope as formally confirmed. Record inferred versus explicitly confirmed scope internally. If the user requests a formal multi-stage project or wants a governance record, present the scope and ask the necessary confirmation before irreversible actions. See [Business-Facing Output Contract](business-facing-output-contract.md).

A user response such as “只做 O” or “O+E” confirms the scope. Store it for the project; never repeat the scope question each turn. A later user request to change scope is itself permission to update the explicit selection; retain history and recalculate affected findings. When the user declines a study or extra mode, don't keep suggesting it absent new decision-critical evidence. Direct professional Skill invocations honor the same authorization: perform only the selected specialization and general-quality prechecks, never silently cross into another specialization.

**Applicability ≠ branch authorization.** Mark a general stage `not_applicable` only with a case-specific explanation and an evidence locator; hide it from the *compact* main path, but keep the reason in expanded detail and event history. “No physical ergonomics involved” is not a reason to omit cognitive ergonomics. Do not mark jurisdiction precheck completely unnecessary without determining locality and actual implementation. If the user insists on an omitted stage, explain its current limits and exactly which documents/parameters/question revision would make it applicable; explicit user reopens the stage, not fabricated result. User preference cannot override binding legal rules.

Suggested research materials, VOC, competitor lookup, data processing, user testing and output formats are never activated by the initial template. The agent can **offer** one narrowly relevant choice, with skip and free-text alternative. Only a real user confirmation can add/start an optional branch. Advancing a common precheck is not approval to collect data, use external sites or launch a product.

## Output contract

Default to a direct professional UX analysis and one consequential next action. Progress maps, collaboration-mode and O/E/D/V record fields are optional output for requested planning, stage review, or formal research handoff, not a first-screen requirement. If a scope clarification changes the decision materially, ask one specific question and preserve the useful preliminary finding. High-risk compliance issues may be warned of immediately; an unread or unverified regulatory item is never “审查完成”.

Offline-first. The user-provided documents and other available evidence set the factual boundary; model inference and cross-industry analogies remain hypotheses. Do not confuse a routable output with completed studies or empirically supported decisions.


## Re-entering O/E after an earlier D report (v0.4D.8)
A D *report delivered* is not a *product decision approved*. In the next O/E map, use `D分析产出：已记录；批准/采纳状态：未确认`, unless a verifiable user/owner decision was actually recorded. Preserve previous D as analysis history while keeping the O/E research open. Do not infer P0/P1/P2, implementation authorization, or regulatory approval from an LLM recommendation. Mandatory read: [O/E Research Scope Integrity](oe-research-scope-integrity.md).

## v0.5A precedence

For a formal new multi-stage project, user-confirmed collaboration mode and study authorization remain separate. For a bounded ordinary UX analysis, infer a provisional working mode and answer without a forced first choice. A user can confirm both with a single message. Do not assume a D/E scope is consent to rapid decision mode. See [Entry Mode Contract](entry-mode-contract.md).
