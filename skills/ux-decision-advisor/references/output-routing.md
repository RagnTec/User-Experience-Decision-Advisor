# D / E / D+E 意图识别（仅供 Router）

| 使用者表达 | 处理 |
|---|---|
| “选 A 还是 B”“要不要重构”“是否值得投入”“优先做什么” | D |
| “用户视角体验如何”“认知负担”“交互好不好”“完整体验总结” | E |
| “既要方案决策，也要详细体验分析”“综合评审” | D+E |
| “帮我看下这个设计”、只有截图而没有要求 | 只问一次选择；如果对话中已有偏好，沿用 |
| “字体清晰吗”“按钮可识别吗”这种单点明确问题 | 直接解决该问题；无需强迫 D/E |

处理优先级：**当前回合明确要求 > 当前会话已确定的模式 > 唯一可推断的明确任务意图 > 一次简短追问**。若用户改变模式，继承原先未变的产品与材料。

选择时用一个正常问题，不先输出庞大菜单；用户答 `D` / `E` / `D+E`、中文同义表达都有效。没有获得授权不要保存任何个人、企业内部材料进入 Skill 本身。


## 注意区分“推断后直接答”和“显式可选分支”

已有足够信息时直接交付并提供可选切换入口；只有真正歧义才阻塞式询问。此前只有文字追问的实现不能保证 Codex 或 ChatGPT 宿主展示真实按钮，采用宿主可用控件或编号文字作为降级。

## v0.3：O（场景与机会发现）的独立入口

- “遗漏了什么场景”“当前需求是否判断错”“能否重新识别机会”→ O，而不是强迫选择 D/E。
- “只要分析当前方案的风险”“只需选择 A/B”→ 分别 E/D；不要因为安装 O 默认调用 O。
- 同时要求找遗漏和决定是否继续推进 → 按需 O+D/E；让 O 的 1–3 项关键发现进入 D/E，而非重复两份清单。
- 只有泛泛“帮我看看产品方向”且无法判定目的时，提供 ①评价现有方案 ②发现遗漏与机会 ③两者结合 三个任务分支；已选择评审但 D/E 不明时才给 D/E/D+E 选择。当前项目已有用户确认的分析范围才直接执行；首次识别到明确倾向时仍要显示 O/E/D/V 并确认是否仅做该方向。
- O 的媒介选择独立于分析内容：未指定时按 `choice-and-format-routing.md` 推荐可交付的形式；用户接受 H5 建议或明确指定 H5 且宿主可创建文件时生成离线页面；拒绝时保持文字；无文件能力时不声称已创建。

**自定义输入**：需要提出分支时，可提供 1–3 个相关候选供快捷选择，并明示用户也可直接键入未列出的目标。用户实际键入的意图优先于预设选项，不要求先选 O/D/E。详见 [动态续谈协议](dynamic-continuation.md)。
