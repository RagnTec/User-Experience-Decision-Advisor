# Shared Router Scope Contract | v0.4D.5

## Single core process; user-controlled analysis tracks

After the explicit collaboration mode is selected (see [Entry Mode Contract](entry-mode-contract.md)), every new Router-driven project uses the same **core decision context**: (1) define user request and real decision; (2) risk-proportionate jurisdiction/platform applicability precheck; (3) cognitive/physical human factors and binding-vs-convention applicability; (4) user/market/task context; (5) existing evidence and unknowns; (6) **user-confirmed analysis scope**; (7) deliver bounded professional result and next user-authorized step. These are professional context checks, not mandatory research tasks. Do not pre-create branches for VOC, surveys, interviews, Kano, market data collection or pilot monitoring.

**O** = explore user task, overlooked needs and candidate opportunities. **E** = evaluate a specified experience/design. **D** = compare alternatives and support a choice. **V** = design or analyze focused validation. All four are **available choices**, not a default mandatory sequence. The same user may select any subset, but a subset is active only after an explicit user choice. An Agent-predicted intent (even when user says “做 O”) is **detected**, not “confirmed only O”. Briefly show O/E/D/V and ask the single relevant scope question: “识别到 O 机会发现；本轮是否仅做 O，还是同时纳入 E、D 或 V？也可自定义。” For ambiguous intent identify the strongest likely scope and ask the same compact question. **Do not generate a full additional unapproved analysis**. You may give a short immediately useful issue framing while awaiting confirmation.

A user response such as “只做 O” or “O+E” confirms the scope. Store it for the project; never repeat the scope question each turn. A later user request to change scope is itself permission to update the explicit selection; retain history and recalculate affected findings. When the user declines a study or extra mode, don't keep suggesting it absent new decision-critical evidence. Direct professional Skill invocations honor the same authorization: perform only the selected specialization and general-quality prechecks, never silently cross into another specialization.

**Applicability ≠ branch authorization.** Mark a general stage `not_applicable` only with a case-specific explanation and an evidence locator; hide it from the *compact* main path, but keep the reason in expanded detail and event history. “No physical ergonomics involved” is not a reason to omit cognitive ergonomics. Do not mark jurisdiction precheck completely unnecessary without determining locality and actual implementation. If the user insists on an omitted stage, explain its current limits and exactly which documents/parameters/question revision would make it applicable; explicit user reopens the stage, not fabricated result. User preference cannot override binding legal rules.

Suggested research materials, VOC, competitor lookup, data processing, user testing and output formats are never activated by the initial template. The agent can **offer** one narrowly relevant choice, with skip and free-text alternative. Only a real user confirmation can add/start an optional branch. Advancing a common precheck is not approval to collect data, use external sites or launch a product.

## Output contract

Start with a compact **业务推进图** showing **协作方式** first, plus a separate **分析范围** line: recognized O/E/D/V vs explicitly selected O/E/D/V. Show current general precheck and stage omission, but no branches created before confirmation. Then give preliminary research meaning, constraints, and **one concise scope confirmation question** when needed. After confirmation, put the substantive analysis under this scope. High-risk compliance issues may be warned of immediately; an unread or unverified regulatory item is never “审查完成”.

Offline-first. The user-provided documents and other available evidence set the factual boundary; model inference and cross-industry analogies remain hypotheses. Do not confuse a routable output with completed studies or empirically supported decisions.


## Re-entering O/E after an earlier D report (v0.4D.8)
A D *report delivered* is not a *product decision approved*. In the next O/E map, use `D分析产出：已记录；批准/采纳状态：未确认`, unless a verifiable user/owner decision was actually recorded. Preserve previous D as analysis history while keeping the O/E research open. Do not infer P0/P1/P2, implementation authorization, or regulatory approval from an LLM recommendation. Mandatory read: [O/E Research Scope Integrity](oe-research-scope-integrity.md).

## v0.5A precedence

The *first user choice* is collaboration mode (guided/decision/review); O/E/D/V remains a separately confirmed research scope. A user can confirm both with a single message. Do not assume a D/E scope is consent to rapid decision mode. See [Entry Mode Contract](entry-mode-contract.md).
