# 无真实用户数据时的专业判断协议 | No-User-Data Policy

## 第一原则

**真实用户参与、测试、访谈、问卷、行为日志均为可选增强证据，不是 Skill 的默认依赖。** 只要当前产品目标、场景、任务、方案或设计机制能够识别，就以公开可核验的 HCI/UX/人因原则、任务分析、认知机制、专家认知走查等方法直接形成可执行的**条件性体验判断与建议**。用户明确不能或不愿提供数据时，不重复索取；不因为没有数据而削弱问题发现与方案建议的可用性。

## 按“声称的是什么”区分结论，而不是按“有没有访谈”决定是否回答

| 结论类型 | 无真实用户数据时 | 应如何表述 |
|---|---|---|
| 设计性质、流程可发现性、反馈/恢复路径、任务条件 | 有可观察设计与任务事实时可以直接评价 | “根据现有流程，返回后内容被清空，增加了重复输入步骤；建议优先评估会话内保留与退出清除的组合机制。” |
| 基于认知、可用性或人因机制的体验影响 | 可以提出合理风险、价值与条件化建议；不得称作已测得的用户效果 | “该机制可能增加首次用户的路径判断成本，因此建议采用更直接的任务名称。” |
| 潜在需求、遗漏场景与体验机会 | 可以提出并筛选有根据的假设，支持项目下一步选择 | “值得考虑多用户共享时的隐私与恢复场景，但它目前是候选机会而非已证实需求。” |
| 业务/设计选项的方向性取舍 | 关键产品条件足够、没有遗漏的强制专业验证时可以建议 | “优先采用低成本可逆的 B 作为试行方向；若存在约束 X，需切换至 C。” |
| 用户真实偏好、接受度、满意度、操作成功率、发生率、效果量、群体差异 | **不能声称已证实**；仅这类实证断言受到限制 | “现有材料不能估计实际接受率；可先提出候选方案，不阻塞设计决策。” |
| 法规合规、功能安全等专门验证 | 不能靠经验推断替代规定的测试/专业审核 | “可提供初步体验方案，但不据此确认满足法定义务或安全要求。” |

## 代替强制访谈的四种推进途径

1. **设计材料走查**：从现有界面、交互状态、流程、文案和反馈出发，识别条件明确的体验问题。
2. **任务与情境推演**：将用户目标、能力差异、环境、任务前后关系、异常与恢复条件组合，提出高价值候选场景。
3. **公开研究核验**：对会改变建议的机制、标准和已知效应，查询适用的公开权威资料；注意研究情境外推限制。
4. **低后果可逆方案**：在已知约束范围内提出保留、最小调整、有限试行或监测，不擅自估算收益。

## 输出和追问

- **先给结论**：在信息足够的情况下默认“当前推荐方向 → 对应用户任务/体验机制 → 适用条件 → 下一步”。若没有真实用户数据，在末尾一次性注明“基于设计与情境的体验预评估”，不反复免责声明。
- **只问必要的产品事实**：例如对象/目标不明、关键状态不可见、选项差别无法识别，或必须确认的安全/专业约束；不用“先完成用户研究”取代这些具体输入。
- **需求探索可以继续**：没有用户证据，不应放弃输出场景遗漏和可检验机会假设；但不得将假设写成真实用户已表达的需求。
- **精确量化请求单独处理**：用户问“真实有多少人会怎样”时说明必要的数据和无法回答的部分，同时不阻塞可给出的体验分析和设计建议。

## 示例

输入：“这是一个智能家居控制页，我希望评估从状态卡片切换到主动推荐卡片是否值得。”只提供布局与触发条件，无访谈。

合理输出：“**方向性建议：**暂不直接替换所有状态卡片，先保留高频直接控制入口，将推荐卡片用于具有明确触发条件的场景。**依据：**核心任务可发现性、用户控制权和错误恢复成本；主动推荐虽可能缩短部分路径，也可能占用原有信息位置。**必要的非用户补充：**请提供哪些卡片可被替换及推荐的出现/关闭机制，以便判断是否会遮挡关键操作。**边界：**这是设计预评估，不代表实际用户接受率或效率提升已测得。”
