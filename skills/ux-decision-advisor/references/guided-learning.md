# Guided learning embedded in problem solving

Use when the user asks to understand a method, concept, research logic, or where to start. Teach through the current problem; do not convert every request into a course.

## 1. Diagnose the actual learning need

Identify whether the user needs:

- a concept clarified;
- a method boundary explained;
- help turning a vague aim into a research question;
- feedback on their own reasoning or material;
- a concrete next practice step.

Do not infer ability, role, or confidence from limited conversation. Adapt only to the question and stated needs.

## 2. Explain with a working example

Use this sequence when helpful:

1. state the practical question;
2. give a concise explanation;
3. show a concrete example from the user's context or a labeled synthetic case;
4. name the common mistake or boundary;
5. offer one next application.

Avoid long histories of the field unless requested. Do not hide the answer behind a quiz.

## 3. Core learning relationships

Help users connect:

- business aim → experience phenomenon → researchable question;
- construct → indicator → data source;
- hypothesis → predicted observation → disconfirming observation;
- method → supported claim → unsupported claim;
- evidence → interpretation → decision consequence;
- resource constraint → feasible design → narrower conclusion.

Use plain language first and technical terms second. Preserve distinctions such as correlation versus causation and self-report versus observed behavior.

## 4. Common method misconceptions

Address only those relevant to the task:

- interviews do not estimate population rates;
- surveys do not directly observe task behavior;
- usability tests do not prove production uplift;
- analytics do not explain intent by themselves;
- more participants do not automatically create valid inference;
- non-significance does not prove equality;
- a pilot is not automatically representative;
- counterbalancing does not eliminate all learning effects;
- expert review is not user research;
- a standard framework is not a universal numeric threshold.

## 5. Coaching without taking ownership

When reviewing a user's plan or question, preserve what is already sound. Explain the concrete defect, its consequence, and a targeted revision. Do not replace their whole approach unless it cannot answer the decision.

Invite the user to test the reasoning on their own material. Offer expansion only when it serves the current task.

## 6. Language adaptation

- Researchers: discuss validity, measurement, and inference directly.
- Product/design partners: emphasize tasks, evidence gaps, and decisions.
- Beginners: define terms briefly and show an example.
- Explicit request for depth: provide the theoretical or methodological detail with sources where needed.

Never simplify by removing a scientific boundary.
