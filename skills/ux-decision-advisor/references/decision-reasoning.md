# Decision Reasoning Core | v0.3

本文件将通用决策质量思路**改造为产品/设计协作的工作方法**，不是将任何政府管理框架视为产品开发中的强制标准。

## 决策入口：七个检查点

1. **定义真实问题**：用户要达成的目标是什么？原始需求是否在暗中预设方案？
2. **约束归属**：有什么已知业务、工程、时间、隐私或专业约束？哪些只是某位协作者的主张？哪些必须转交其他岗位确认？
3. **选项足够宽**：至少检查保留现状、最小改动、实质改造是否真实可行；不要强制凑三个选项，也不要凭空制造功能。
4. **谁获得收益、谁承担负担**：分析典型任务与可能被牺牲的人群/情境；频率与范围未知时不估算。
5. **决定性证据**：真正能够区分选项的事实是什么？已有来源是否足够直接？
6. **可逆性与后果**：可快速回退的局部改变与不可逆、高后果改变应采用不同的证据门槛。不要用“风险高”自动证明某一设计必需。
7. **行动权与停止规则**：可作出何种有条件决定？什么新结果会触发重新评审？由谁确认非 UX 约束？

## 决策结果必须允许的动作

- **Keep / 保留现状**：问题不关键、收益未证实，或当前方案有重要优势；说明观察条件。
- **Do minimum / 最小改动**：低成本、目标明确、可逆且无额外安全约束；仍需核查回归影响。
- **Compare / 并行比较**：两方案取舍不同且现有证据不足。
- **Pilot / 定向试跑**：未知很可能改变方案选择，且可低成本通过实际任务观察得到信息。
- **Hold / 暂缓**：重要决策条件不成立，或成本/证据不够，不是“没发现任何问题”。
- **Escalate / 转专业审查**：可能涉及安全、法定要求、隐私、受保护群体或非 UX 责任。

不能将以上类别转换成唯一“综合设计得分”。只在必要时列出互不合并的比较维度。

## 比较方案的最小表述

`方案 | 最可能改善的目标 | 体验代价与副作用 | 已知实施约束 | 支持依据 | 对结论最不利的反例 | 可逆性/验证`。

- 若用户要求“推荐一个”，可以基于已知条件给**有条件的方向**，但不能制造没有观测或实施资料的成本收益。
- 若无法形成比较，说明**可支持的局部建议**与**无法支持的总体胜负**。
- “没有数据”不等于必须先做大规模调查；“主观上很明确”也不等于无需验证。

## 要不要继续研究：决策相关未知（Decision-Critical Unknowns）

对每一项缺失信息，只保留两类：

- **决策关键未知**：新证据的不同结果可能使选项从 A 变 B、从实施变暂缓，或者影响重要风险接受；优先判断能否由现有产品材料、设计推理、公开依据或非用户方式澄清，真实用户研究只是一种可选取证手段。
- **背景性未知**：缺少但不会改变当前最小下一步，可记录并暂缓收集。

操作步骤：写出 `若观察到 X，倾向 A；若观察到 Y，倾向 B`；无法写出这种分支时，先检查是否真的需要研究。必要时用小规模探索/可用性任务/日志核对等获得方向性证据。**与法定验证、重大危害或不可逆风险有关的任务不可据此简化豁免。**

没有可信概率、损失和研究成本时，不计算 Expected Value of Information，不对“节约多少资源”作数字化承诺。

## 决策质量检查（质性）

- Framing：是否讨论对了问题？
- Alternatives：是否存在真正不同且可执行的路径？
- Information：证据是否可信、完整到足以支持当前选择？
- Values/Trade-offs：是否说清目标优先次序和不同受益者？
- Reasoning：建议是否可以由事实、机制与约束推导？是否存在反例？
- Commitment：谁负责落地与何时回看？仅在输入有负责人/期限时具体化，不自行指派。

## 停止条件

当核心选项和逆转条件已说明、剩余未知不影响本次决定、且无强制专业义务时，停止继续展开无收益的体验细节。若使用者明确要求 E 详细说明体验机制，则不因为 D 已完成而截断 E。
